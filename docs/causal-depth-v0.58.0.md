# v0.58.0 — Causal depth: одна история оплаты

## Объём

Полностью прочитаны задание и аудит v0.57.4. Изучены prepareEncounter, roleRouting, storyScenes, paymentChain, sceneConsequences, технические действия и артефакты, разговоры, history, мастерство и regression suites.

Изменяется одна вертикальная история: оплата, начатая Frontend, её коллеги и наследование исправления. Остальные problem domains продолжают использовать существующий routing. Никакого общего редизайна, новых профессий, магазина или экономики. Коэффициенты стресса, XP-настройки и пороги карьеры не меняются.

## Что причинно, а не по счётчику

После входа в эту цепочку prepareEncounter выбирает работу по paymentCausal.phase/cause, paymentChain и событиям, вызванным результатами. count % families не используется для этой вертикали. Первая ситуация Junior сохраняет знакомый стартовый lens; свежая ситуация и продолжение различаются по реальным предыдущим фактам.

Сохраняются:

- encounter.cause, recurrenceKind и previousDecisionId;
- исходная задача, последняя задача, решение и референсы на прежнего героя;
- конкретное ограничение: потеря ответа, непроверенный pending, заблокированные pending-платежи;
- принятый риск, согласованный scope, версия Backend-контракта и ревизия работы коллеги;
- ожидаемые события с датой, источником и конкретным коллегой;
- физические наблюдаемые счётчики дублей и pending в инциденте;
- ответ зависимости, её получатель, срок и факт доставки новой версии.

Старый paymentChain восстанавливает причину из сохранённого обхода/исправления, не из названия шаблона. Статус старого подтверждённого исправления не превращается обратно в неизвестный баг.

## Различные рабочие структуры

### Dependency

Гипотеза клиента и гипотеза контракта — разумные начальные направления. Ответ реального Backend сообщает, что исходная операция существует: гипотеза только о кнопке недостаточна. После ответа доступны проверка контракта и сопоставление с QA; прежний прямой набор действий не продолжается автоматически.

Ожидание можно провести подготовкой сравнения запросов (30 игровых минут) или приостановить задачу существующим механизмом и делать другую работу. Ответ и уже прочитанные данные сохраняются при reload.

### Review

Игрок читает конкретный diff коллеги: после timeout предложение создаёт новый ключ. Можно принять ограниченную проверку с риском либо отправить воспроизводимое замечание. Ревизия коллеги меняется только после срока ответа. Перед одобрением требуется прочитать новый diff и проверить результат. Можно вместо одобрения запросить отдельную проверку QA — это порождает следующий эпизод с данными, а не текстовую галочку.

Одобрение кода не уменьшает project.techDebt и не завершает физически pending-платежи. Если они остаются после containment, зависимость остаётся открытой. Review изменяет работу коллеги, но не выдаётся за деплой исправления.

### Incident

Принятый риск непроверенного pending приводит к новому воспроизведению. Ограничение повторов ещё не завершает задачу: требуется контрольное окно и просмотр метрик. Наблюдается частичный эффект — новых дублей нет, но семь платежей pending. Игрок либо запрашивает данные для продолжения, либо принимает цену сохранённого ограничения. Последующая задача получает ссылку на это решение.

### External change

После проверенной работы коллеги Backend вводит другой адрес проверки состояния: ответ pending содержит statusUrl. Прежний обработчик обращается к старому адресу и получает 404. Это не повтор первоначального бага кнопки и не просто другой номер версии.

Артефакты показывают новый контракт, воспроизведение QA и проверку обработчика, читающего адрес из ответа. Новый герой видит также проверку statusUrl при наследовании исправления.

## Грейды и разговоры

- Junior исследует узкий участок исходной проблемы.
- Middle получает альтернативные гипотезы.
- Senior может сопоставить конфликтующие локальное воспроизведение и общую метрику.
- Lead после существующих вводных лидерских задач может передать проверку конкретному Backend с условиями приёмки. Занятость коллеги не создаёт фиктивное делегирование: остаётся запрос данных и собственная ответственность, с явным пояснением.

В нескольких рабочих разговорах текущей оплаты предлагаются различные позиции: запросить evidence, договориться о меньшем scope у Product, принять ограничение и продолжить выпуск. Они создают разные последующие события. Эти разговоры не получают общей награды trust/communication за любой ответ. Остальные личные разговоры не перерабатывались.

Точечная проверка начисления опыта для нового causal-delegate требует реально созданной delegationId; пороги mastery и остальная карьерная модель не менялись.

## История и артефакты

Используются существующие IDE / Browser / Console / Chat и renderer профессиональных артефактов. Review открывается в IDE, incident — Console, исследование запросов — Browser. Новых приложений или декоративных scene families нет.

Сцена сохраняет собственный snapshot артефактов. Перемены мира не переписывают уже открытый старый diff. Раскрываемая история дополнена известным контекстом причины текущей встречи; скрытый rootCause не отображается. Старые результаты, действия и ограничения остаются в encounter history.

## Доказательная цепочка из десяти эпизодов

Сохранён engine trace: `docs/causal-depth-v0.58.0-trace.json`.

| Эпизод | Причина | Работа |
|---|---|---|
| 1 | fresh_problem | Локальный обход, оставивший потерю ответа вне границы |
| 2 | qa_reproduction | QA вернулась к исходному решению; его долг закрывается проверенным исправлением |
| 3 | returned_review | Конкретный diff коллеги возвращается на переработку; запрашивается QA |
| 4 | qa_reproduction | Ответ и артефакт расширяют разбор; ограничение передаётся без фиктивного исправления |
| 5 | unresolved_limit | Product согласовал меньший scope; игрок принимает риск выпуска |
| 6 | accepted_risk | Данные инцидента, containment, контрольное окно, частичный эффект |
| 7 | qa_reproduction | Данные по оставшемуся pending приводят к проверенному исправлению |
| 8 | backend_contract | Новый statusUrl и 404 старого адреса требуют другого изменения |
| 9 | qa_reproduction | Проверяется независимое воспроизведение нового контракта, затем исправление |

У каждого продолжения есть previousDecisionId; все эпизоды привязаны к одному problemId. В trace сохранены реальные action histories, observations, последствия, ревизии и события.

Это движковая fixture с намеренной привязкой задач к одной оплате и контролем времени. Она доказывает причинную достижимость, но не является естественной пользовательской партией: очередь не выбирает сама десять оплат подряд, а следующий QA в этом тесте назначается напрямую. Отдельный существующий paymentChain test проверяет реальный hire и onboarding следующего героя. Живой плейтест интереса и ручной browser-прогон всей цепочки не проводились.

## Проверка

396 tests / 64 files прошли; production build прошёл. Добавлены 12 targeted regressions:

- ограничение обхода и независимость выбора сцены от encounter count;
- опровержение гипотезы ответом конкретного Backend и новый набор действий;
- review comment → доставка новой ревизии → чтение diff → verification;
- принятый риск → incident → наблюдение частичного эффекта → следующее решение;
- новая версия контракта действительно содержит statusUrl/404;
- различные рабочие разговоры дают различные события без общей численной награды;
- десять связанных эпизодов с причинными референсами;
- различия ответственности по четырём грейдам;
- история не раскрывает скрытый rootCause;
- занятый коллега не даёт опыта фиктивной delegation;
- review не очищает физические pending;
- граф recurrence не содержит несуществующих next actions ни на одном грейде.

В generic story regression fixtures для проверки прежнего циклического variety использована область interface вместо payment. Старые проверки generic review, dependencies, измерений и истории сохранены. Отдельные старые paymentChain и новые causal tests продолжают проверять оплату. Это разделение области, которую намеренно изменили, и остальных сценариев; проверки не удалялись.

## Практические границы

Количества в небольших артефактах — детерминированная модель, не реальная сеть. Пока реализованы конкретные ответы и исходы выбранной цепочки; общего генератора неполных/задержанных ответов для всех professions нет. За пределами этой вертикали прежний count-based routing остаётся.

Следующая проверка — естественный прогон этой цепочки с читающим игроком: способен ли он объяснить, какое его решение привело к следующему эпизоду, и хочется ли попробовать иной путь. Только после этого переносить подход на остальные области.
